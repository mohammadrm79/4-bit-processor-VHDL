# Testing Framework

## Overview

The RISC-4 Educational CPU includes an automated testing framework for validating every supported instruction and verifying the complete processor behavior.

The testing flow is fully automated and consists of:

1. VHDL analysis
2. Assembly generation
3. CPU simulation
4. Result extraction
5. Expected output comparison
6. Test summary generation

Running a single command verifies the entire processor.

```bash
make test
```

or

```bash
./scripts/test.sh
```

---

# Test Directory Structure

The testing infrastructure is organized under the `tb/` directory.

```text
tb/
├── integration/
│   └── tb_cpu.vhdl
│
├── unit/
│   ├── tb_alu.vhdl
│   ├── tb_control.vhdl
│   ├── tb_ir.vhdl
│   ├── tb_pc.vhdl
│   ├── tb_register_file.vhdl
│   └── ...
│
└── programs/
    ├── test.lst
    ├── program_test.mem
    ├── asm/
    ├── bin/
    ├── out/
    └── exp/
```

# Unit Tests

The `unit/` directory contains isolated tests for individual hardware modules.

Current unit tests include:

| File | Module |
|------|--------|
| tb_alu.vhdl | Arithmetic Logic Unit |
| tb_control.vhdl | Control FSM |
| tb_ir.vhdl | Instruction Register |
| tb_pc.vhdl | Program Counter |
| tb_register_file.vhdl | Register File |
| ... | ... |

Each testbench verifies a single hardware block independently.

---

# Integration Test

The integration test executes the complete CPU.

```text
tb/integration/tb_cpu.vhdl
```

This testbench loads an assembled program into instruction memory and runs the processor until the HALT instruction is executed.

After execution it reports:

- PC
- Registers
- Flags
- Halt state

---

# Test Programs

Every processor instruction has its own test program.

Location:

```text
tb/programs/asm/
```

Example:

```text
add.asm
sub.asm
movi.asm
jump.asm
jz.asm
jc.asm
...
```

Each assembly program verifies exactly one processor feature whenever possible.

---

# Assembly Files (.asm)

Assembly source files describe the program executed by the processor.

Example:

```asm
MOVI R0,5
MOVI R1,2
ADD R2,R0,R1
HALT
```

These files are human-readable and are assembled before simulation.

---

# Machine Code Files (.mem)

Generated by:

```text
assembler.sh
```

Location:

```text
tb/programs/bin/
```

Example:

```text
1805
1902
0250
8800
```

These files are loaded directly into the instruction memory during simulation.

---

# Expected Output Files (.exp)

Expected CPU state after program execution.

Location:

```text
tb/programs/exp/
```

Example:

```text
HALTED=1
PC=4
REG[0]=5
REG[1]=2
REG[2]=7
REG[3]=0
FLAG[ZERO]=0
FLAG[CARRY]=0
```

The expected output represents the correct architectural state of the processor after executing the corresponding assembly program.

---

# Simulation Output Files (.out)

Generated automatically during testing.

Location:

```text
tb/programs/out/
```

Example:

```text
HALTED=1
PC=4
REG[0]=5
REG[1]=2
REG[2]=7
REG[3]=0
FLAG[ZERO]=0
FLAG[CARRY]=0
```

These files contain the actual CPU state produced by simulation.

---

# Test List File (test.lst)

The `test.lst` file contains the list of all test programs included in the project.

Each line in this file specifies the name of a single test.

Example:

```text
movi
add
sub
load
store
jump
jz
jc
```

The `test.sh` script reads this file and executes every listed test in sequence.

To add a new test, simply add its name to this file.

# Output Comparison

For every test:

```
.asm
   │
   ▼
assembler.awk
   │
   ▼
.mem
   │
   ▼
Instruction Memory
   │
   ▼
CPU Simulation
   │
   ▼
.out
   │
   ▼
diff
   │
   ▼
PASS / FAIL
```

The generated `.out` file is compared against the corresponding `.exp` file.

If both files are identical:

```
PASS
```

Otherwise:

```
FAIL
```

and the exact differences are displayed.


# Adding a New Test

To add support for a new instruction:

1. Create an assembly program.

```
tb/programs/asm/new_instruction.asm
```

2. Define the expected CPU state.

```
tb/programs/exp/new_instruction.exp
```

4. add the test name, such as `add` for `add.asm`, to `tb/programs/tests.lst`
3. Execute:

```bash
make test
```

The framework automatically:

- assembles the program,
- simulates the CPU,
- compares the output,
- includes the new test in the summary.

No modification to the test runner is normally required.

# Notes

- Every instruction should have at least one dedicated test.
- Tests should verify only one processor feature whenever possible.
- Expected results must be deterministic.
- All generated test artifacts are written under the `tb/programs/out` directory.
- Integration tests verify complete processor functionality, while unit tests verify individual hardware modules independently.
